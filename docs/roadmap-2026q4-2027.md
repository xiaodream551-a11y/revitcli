## 1. 全景图

下一年 7 个版本,**3 个主题集群**:

```
v2.1 ─┐
v2.2 ─┼─ Confidence (cluster):已铺能力的可信度
v2.3 ─┘   (生产可信、可签名、可调试)

v3.0 ─┐
v3.1 ─┼─ Network + Intelligence (cluster):从单机到组织,从写规则到生成规则
v3.2 ─┘   (跨项目分发、AI 协助、生命周期感知)

v4.0 ──── Platform:从工具到生态(插件 + 沙箱)
```

| Version  | 主题                       | 一句话目标                                           | 工程量 | 风险 | 创新度 |
| -------- | -------------------------- | ---------------------------------------------------- | ------ | ---- | ------ |
| **v2.1** | Configuration Confidence   | profile / smoke / journal 三条已交付能力都可生产可信 | 中     | 低   | 中     |
| **v2.2** | Attestation & Provenance   | 交付物加密签名,合同纠纷有底气                        | 中     | 低   | 高     |
| **v2.3** | Anomaly Detection          | history 数据用起来:bisect、异常检测、趋势告警        | 中     | 低   | 中     |
| **v3.0** | Profile Federation         | 从 single-repo profile 到 org-level registry         | 大     | 中   | 中     |
| **v3.1** | AI-Assisted Rule Authoring | profile 写不出来?CLI 帮你或建议你                    | 中-大  | 中   | 高     |
| **v3.2** | Lifecycle-Aware Profiles   | 设计 / 招标 / 施工 / 移交 各阶段不同标准             | 中     | 低   | 中     |
| **v4.0** | Plugin Ecosystem           | 用户自定义 rule / fix strategy,WASM 沙箱执行         | 大     | 高   | 高     |

**为什么这个顺序**:

- **v2.x 全做"深化"**(没有新动词)— 让 v1.x → v2.0 已经铺出来的能力变成"客户敢用"
- **v3.x 引入"网络 / 智能"** — 从单机到组织、从手写到生成、从静态规则到动态生命周期
- **v4.0 才打开生态** — 等社区有需求 + 内部架构稳定再放开第三方代码

### v2.1 step 2 — 多 Revit 版本 smoke 矩阵(给 codex)

#### 价值

README 声称支持 2024 / 2025 / 2026 但 CI 只跑 2026。"多 Revit 版本支持"在
项目战略定位里是**核心差异化**,但目前是**声称未验证**的状态。

#### 范围(In)

- `scripts/smoke-revit.ps1 -Version 2024|2025|2026` — 参数化,替代当前的
  `smoke-revit2026.ps1`
- 新 `.github/workflows/smoke-matrix.yml`(模板,放在 `docs/ci/`)
  - 触发条件:operator 自定义(默认 `workflow_dispatch` + `schedule: cron`)
  - 矩阵:`runs-on: [self-hosted, windows, revit-{2024,2025,2026}]`
  - 每个 leg 跑 smoke 脚本,产出 SARIF + 兼容性 JSON
- 新 `docs/compatibility-matrix.md` — 哪些命令 / 端点 / API 在哪些 Revit 版本生效
- `revitcli doctor` 增加 `--check-version <2024|2025|2026>`,本地预检版本兼容

#### 范围(Out)

- 不真在 CI 跑(项目仓本身没 self-hosted Windows runner)— 只发模板
- 不做 2027 / 2028 前瞻 — Revit 出新版本再说

#### 关键决策

**决策 1:smoke 失败时怎么报?**

候选 A:整个 leg 退出 1,job 红
候选 B:每个命令 leg 单独 marker,产 partial-success matrix

**结论:候选 B**。多版本 smoke 的价值就是"哪个版本哪个命令坏了"的精确信号。

**决策 2:测试模型从哪来?**

候选 A:每个版本一个 ground-truth `.rvt`(repo 里 LFS)
候选 B:operator 自带 `.rvt` 路径,smoke 脚本接受 `-ModelPath` 参数

**结论:候选 B**。LFS + 多版本 .rvt 是一颗炸弹。模板化让 operator 用自己的。

#### 实施分步

1. **Spec**(0.5d):列出 smoke 必跑的命令 + 失败语义
2. **PowerShell 参数化**(1d):重构 `smoke-revit2026.ps1` 为 `smoke-revit.ps1 -Version`
3. **CI 矩阵 workflow 模板**(0.5d)
4. **兼容性 doc 框架**(0.5d):一张表,行=命令,列=版本
5. **`doctor --check-version`**(0.5d)
6. **测试 + 文档**(0.5d)

#### 验收

- [ ] smoke 脚本 `-Version` 参数化,3 个版本各跑通(operator 验证)
- [ ] 矩阵 workflow 模板可 copy + adjust 即跑
- [ ] 兼容性 doc 列出至少 5 条已知差异(`schedule create` 在 2024 / `family export` 在 2026 等)

#### 给 codex 的入口

### v2.1 step 3 — Journal signing + verify(给 codex)

#### 价值

`.revitcli/journal.jsonl` 是 append-only 但**无签名**。法规 / 高严肃场景
(医院、政府 AEC、上市公司 BIM)需要不可篡改的审计日志:

- 检察官:"3 月 12 日的图纸是否真的在那时候生成的?"
- 客户:"这个 publish 是不是后改的?"
- 项目经理:"团队成员有没有事后修过 fix journal?"

#### 范围(In)

- `revitcli journal sign [--key <path>] [--out <path>]` — 产出 SHA256-chained
  Merkle 风格的签名文件 `journal.jsonl.sig`
- `revitcli journal verify [--key <path>]` — 重 walk journal + .sig,报告
  任何 entry 插入 / 删除 / 修改
- 默认本地 HMAC(无密钥参数,从 `.revitcli/journal.key` 读 — 写在 .gitignore)
- 可选 RFC 3161 timestamp 集成(`--rfc3161 https://...`)
- 可选 Sigstore 集成 — 公钥流(stretch,放 v2.2 attestation 章一起)

#### 范围(Out)

- 不做用户认证(谁签名是 ops 流程的事)
- 不做 GUI 验证工具 — CLI 够了
- 不做 journal 加密 — 签名 ≠ 加密,加密走另一条线

#### 关键决策

**决策 1:签名粒度?**

候选 A:每条 entry 单独签 — 校验 expensive
候选 B:整文件单签 — append 时所有旧签作废
候选 C:Merkle 链 / hash chain — 每个 entry 含上一行 hash + 整文件 root

**结论:候选 C**。append 友好,verify O(n) 顺读,与 git commit chain 同款思路。

**决策 2:密钥管理?**

候选 A:`.revitcli/journal.key` 本地文件(默认)— 简单,不安全(本地泄露)
候选 B:OS keychain — 复杂,跨平台辛苦
候选 C:外部 KMS 引用 — 企业级

**结论:A 起步,留 `--key` flag 接 B/C 的扩展**。日常 BIM team 不需要 HSM。

#### 实施分步

1. **Spec**(0.5d):签名 schema,verify 失败信号 taxonomy
2. **JournalSigner / JournalVerifier 核心**(1d,纯 C#)
3. **`journal sign` / `journal verify` 子命令**(0.5d)
4. **HMAC 默认密钥流**(0.5d)
5. **测试**(1d):合法 / 篡改 / 半截 / 链断
6. **文档**(0.5d):`docs/journal-signing.md` + 法规场景说明

#### 验收

- [ ] sign 后 verify 通过
- [ ] 修改任意一条 entry 后 verify 报错并定位
- [ ] 删除任意一条 entry 后 verify 报错
- [ ] 在 sig 后追加新 entry,verify 区分"已签"和"未签"段

#### 给 codex 的入口

```bash
"用 superpowers:writing-plan 写 v2.1 step 3 journal signing 实施计划.
参考 docs/v2.1-roadmap.md §1 step 3.
关键决策:Merkle hash chain 粒度 + HMAC 默认密钥流."
```

## 3. v2.2 — Attestation & Provenance

### 价值主张

AEC 合同交付物常因"这是哪个版本的 model 产生的"扯皮:客户说图改过,设计师说没。
v2.2 借 SLSA / Sigstore 的供应链 attestation 思路,给 publish 输出一份**可验证
的 provenance 清单**:

```bash
revitcli publish client-A --attest
# 产出:
#   exports/client-A.dwg
#   exports/client-A.dwg.attest.json     # provenance manifest
#   exports/client-A.dwg.attest.json.sig # 签名(沿用 v2.1 step 3 的 chain)

revitcli verify exports/client-A.dwg
# 输出:
#   ✓ Manifest:           exports/client-A.dwg.attest.json
#   ✓ Profile hash:       SHA256:abc... (matches .revitcli.yml at 2026-05-12T10:00Z)
#   ✓ Snapshot hash:      SHA256:def... (matches snapshot/at-publish.json)
#   ✓ Git commit:         f3a2b1...    (matches origin/main HEAD at signing)
#   ✓ Signature:          chain-valid, signer=alice@bim-team.example
```

### 创新度(为什么 AEC 没人这么干)

软件供应链有 SLSA / Sigstore / cosign;AEC 行业**完全没有**等价物。BIM 模型流动
中"哪个版本的什么标准产出哪个交付物"靠**Excel 跟踪表 + 设计师记忆力**。把
software supply chain 的 provenance 思想移植过来是 RevitCli **真正的护城河之一**
(社区 MCP server 完全不在这个赛道)。

### 范围(In)

- `revitcli publish --attest` — 每个 export artifact 产出对应的
  `<artifact>.attest.json`
- attest manifest schema(基于 [in-toto v1.0](https://in-toto.io/) 风格,简化):
  ```json
  {
    "version": 1,
    "subject": [{ "name": "client-A.dwg", "digest": { "sha256": "..." } }],
    "predicate": {
      "predicateType": "https://revitcli.dev/attest/v1",
      "buildType": "revitcli-publish",
      "builder": { "id": "revitcli@1.x" },
      "metadata": {
        "buildStartedOn": "...",
        "buildFinishedOn": "...",
        "profileHash": "sha256:...",
        "snapshotHash": "sha256:...",
        "gitCommit": "...",
        "gitRef": "refs/heads/main"
      },
      "materials": [
        { "uri": ".revitcli.yml", "digest": { "sha256": "..." } },
        { "uri": "snapshot/at-publish.json", "digest": { "sha256": "..." } }
      ]
    }
  }
  ```
- `revitcli verify <artifact>` — 自检 + 跨工件验证
- `revitcli verify --bundle <dir>` — 验证整个 publish output 一致性
- profile schema 加 `defaults.attest: { enabled, signer, signKey }`

### 范围(Out)

- 公钥基础设施(PKI / CA chain)— 留给企业部署 ops
- Sigstore transparency log — 可选 stretch,不是必需
- 跨语言 attest 验证客户端 — Python / JS SDK 是 v3.x 的事

### 关键决策

**决策 1:attest 是 publish 的 flag 还是独立后处理?**

候选 A:`publish --attest`(嵌入)
候选 B:`publish` 后 `attest publish-output/`(独立)

**结论:A**。publish 进程拥有 profile / snapshot 的 in-memory 状态,后处理要重新读;
而且 operator 习惯一个命令搞定。

**决策 2:manifest schema 与 in-toto 关系?**

候选 A:严格 in-toto v1.0 — 兼容 cosign 验证
候选 B:revitcli-flavored 简化 — 易读但不通用

**结论:A 起步**。verifier 兼容 cosign 是大杀器(operator 已有的 sigstore 流可以直接用)。

### 实施分步

1. **Spec**(1d):in-toto-flavored manifest schema + verify 失败 taxonomy
2. **AttestBuilder 核心**(1d):publish 流程里收集 profile/snapshot/git 状态
3. **`publish --attest` 集成**(1d)
4. **`verify` 子命令**(1d):manifest 解析 + digest 重算 + 签名校验
5. **测试**(1.5d):合法 / 篡改 manifest / 篡改 artifact / 缺失 material / 签名错
6. **文档**(1d):`docs/attestation.md` + 一个端到端示例

### 风险

- **manifest 大小** — 大模型 publish 一次产 5 个 artifact,5 份 manifest;每份 ~1KB,
  可控
- **profile hash 抖动** — YAML 序列化变种导致 hash 不稳定;**必须**用 canonical
  serialization(已有 ProfileResolver)
- **git commit 来源不可靠** — 不在 git repo 时降级到 directory hash + 标记
  `gitCommit: null`

### 给 codex 的入口

```bash
"用 superpowers:brainstorming 探索 publish provenance manifest 设计.
读 https://in-toto.io/specs/v1.0 了解 schema. 关键决策:in-toto 严格 vs flavored."
```

## 4. v2.3 — Anomaly Detection

### 价值主张

v1.6 把 history 仓库化了 — 但目前用法只有 `history list / diff / trend`。
真实操作场景:

- "上周开始 score 跌了 5 分,哪一天发生的什么?" — 现在要手动 walk diff
- "周一突然有 100 个房间没了 — 谁干的、什么时候?" — 现在 history 看不出来
- "新添了一组复杂族,出在哪个 capture?" — 需要 git bisect 风格的二分

### 创新度

- `git bisect` 移植到 BIM model history(没人做过)
- 异常检测在 BIM 是新概念(industry 里 "model checking" 是规则驱动,不是统计驱动)

### 范围(In)

- `revitcli history bisect <metric> <expected> <actual>` — 二分查找 metric
  值变化的 capture
- `revitcli history anomaly [--metric M] [--window W]` — 滑动窗口 z-score 异常
  检测,标记可疑 capture
- `revitcli history blame <capture-id>` — 该 capture 与上一个相比,what changed
  (重用 v1.1 SnapshotDiffer)
- profile 加 `history.anomaly.thresholds` 节点 — operator 调灵敏度
- score 时间序列加 anomaly markers(给 dashboard 接驳)

### 范围(Out)

- 通知 / 告警 — 走已有 webhook,不重复造
- ML 异常检测 — 简单 z-score 已经够用,深度 model 留给真有需求时

### 关键决策

**决策 1:bisect 二分的相等比较语义?**

候选 A:数值精确等
候选 B:数值容差(`±N`)
候选 C:metric 函数自定义

**结论:A 默认 + `--tolerance N` 选项**。绝大多数 metric(score、element-count)是
整数。

**决策 2:anomaly 用 z-score 还是 IQR?**

候选 A:z-score(`(x - μ) / σ`,需正态假设)
候选 B:IQR(四分位距,鲁棒性强,更适合 BIM 数据)

**结论:候选 B (IQR)**。BIM 数据(element-count、sheets)经常长尾,z-score 误报多。

### 实施分步

1. Spec(0.5d)
2. `HistoryBisector`(0.5d)
3. `AnomalyDetector`(IQR + window)(1d)
4. `HistoryBlame`(复用 SnapshotDiffer)(0.5d)
5. CLI 子命令 3 个(1d)
6. profile schema 扩展(0.5d)
7. dashboard markers(0.5d,可选)
8. 测试 + 文档(1d)

### 给 codex 的入口

```bash
"用 superpowers:brainstorming 设计 history bisect / anomaly 命令组.
读 src/RevitCli/History/HistoryStore.cs 和 src/RevitCli/Snapshot/SnapshotDiffer.cs.
关键决策:bisect 容差 + IQR vs z-score."
```

## 5. v3.0 — Profile Federation

### 价值主张

v1.9 `profile install <git-url>` 让 profile 共享变成"知道 URL 就能装"。但
**发现性**仍然是零:

- 公司 100 个 BIM team,每队都自己写 profile,水平参差
- 行业最佳实践(ISO 19650、UK NBS、AIA)没有"装即用"包
- 团队级 profile registry 没有(每个 team 的 wiki 上一份 README,过时)

v3.0 把"profile 是 git URL"升级成"profile 是 registry artifact",有名字、版本、
搜索、依赖。

### 创新度

类比:

- npm 之前 — 每个 JS 库写自己的 setup.sh
- npm 之后 — `npm install lodash`

BIM 的 profile registry 是**业界从未存在过的东西**。如果做对,RevitCli 团队就
controlled 了 industry standards 的发行渠道(像 npm 控制了 JS 生态)。

### 范围(In)

- `revitcli profile search <query>` — 在 registry index 中按 tag / 描述查找
- `revitcli profile install <name@version>` — 简短名(覆盖 v1.9 的 git-url 路径)
- registry index 协议(开放 spec):JSON file at well-known path
  - 默认:`https://registry.revitcli.dev/index.json`(项目运营)
  - 可加私有:`profile.registries: [https://internal/registry.json, ...]`
- profile metadata 文件:`profile.meta.yml`(name / version / tags / depends)
- `revitcli profile publish` — 推 profile 到 registry(走标准 git push,index 自动更新)
- 起步种子:RevitCli 团队维护 ~10 个公共 profile(ISO 19650 子集、AIA C202、
  常见住宅 / 商业模板)

### 范围(Out)

- 中央付费 SaaS — 永远不
- profile 的 RBAC — registry 协议外的事(走 git host 的 ACL)
- profile market(付费 / 评分)— v4.x 再说

### 关键决策

**决策 1:registry 是中央还是去中心?**

候选 A:中央 hub(类 npmjs.com)
候选 B:去中心 list(类 git remotes)

**结论:候选 B + 项目维护一个公共 default**。AEC 数据隐私敏感,operator 必须能加私有 source。

**决策 2:版本 / 依赖语义?**

候选 A:semver(类 npm)
候选 B:git tags(类 go modules pre-1.0)
候选 C:无版本(rolling)

**结论:候选 A**。profile 不是代码,但 semver 在 ops 心智里已是 universal — 用现成的最少阻力。

### 实施分步

参见 v3.0 spec(待写)。预计 6 周(spec 1w, registry 协议 1w, CLI 2w, seed profiles 1w, 测试 + 文档 1w)。

关键问题:registry 协议是 list 还是 hub,版本是 semver 还是 git tags."

## 6. v3.1 — AI-Assisted Rule Authoring

### 价值主张

写 profile 是 RevitCli 现在最高的入门门槛 — operator 要懂 YAML schema、Revit
category 名、规则语义。**降低这个门槛**直接放大用户基数。

两条路:

1. **`profile suggest`(被动)** — 看 operator 现有 model,统计模式,提议 profile 规则
2. **`profile assist`(主动)** — 自然语言交互,operator 描述标准,CLI 生成 YAML

### 创新度

`suggest` 是**纯统计**:扫 history,看哪些参数在 80%+ 元素上非空,推荐成
`required-parameter` 规则。完全不依赖 LLM。这是真正实用的 BIM-domain ML。

`assist` 是 **MCP-driven**:用已有的 sampling / tool 协议,server 反向问 LLM
client "operator 描述了这条规则,请帮转 YAML"。复用 PR #23 的 sampling
管道(那是为这一刻铺的路)。

### 范围(In)

- `revitcli profile suggest [--category X] [--snapshot S]` — 输出 YAML 片段
  - 推荐理由 + 数据支撑("Mark 在 1234/1280 个 doors 上非空 = 96%")
- `revitcli profile assist` — 交互模式;只在配了 MCP 客户端时启用
- 启发式库(C#):required-parameter / naming-pattern / category-hint / fix-strategy
- "导师" UX:每条建议都带 "why" 和 "would affect N elements"

### 范围(Out)

- 全自动写 profile(不行,需 human review)
- 跨 model 汇总(`suggest` 只看一个 model;federation 留给 v3.0)

### 关键决策

**决策 1:`suggest` 输出 inline patch 还是独立 `profile.suggest.yml`?**

候选 A:patch 当前 profile(自动写)
候选 B:独立文件,operator 手 merge

**结论:候选 B + `--apply` flag 显式开 A**。AEC 标准是合规事项,默认绝不自动改。

**决策 2:`assist` 走 MCP sampling 还是直接 OpenAI / Claude SDK?**

候选 A:MCP sampling(走 client 的 LLM,operator 已配置)
候选 B:直接 SDK(operator 提供 API key)

**结论:候选 A**。复用已有 MCP 安全模型 + 不强加 SaaS 依赖 + 不收 LLM 费用。

### 实施分步

预计 4–5 周。详细 spec 待写。

### 给 codex 的入口

```bash
"用 superpowers:brainstorming 设计 profile suggest.
重点:用 history 数据怎么生成有说服力的规则建议."
```

## 7. v3.2 — Lifecycle-Aware Profiles

### 价值主张

AEC 项目有清晰的阶段:**设计 → 招标 → 施工 → 移交**。每阶段对模型的标准
不同:

- 设计阶段:粗略 element 计数 OK,房间编号还能改
- 招标阶段:房间编号锁定,Mark 必填,导出 PDF 含图签
- 施工阶段:门窗五金参数必填,材料代码锁定
- 移交阶段:全字段填齐,IFC 导出可校验

当前 profile 是**flat 的**,operator 要么写 4 个 profile 文件来回切,要么忍受
"早期严格 / 后期宽松"的不合理标准。

### 创新度

- 引入"阶段"作为 profile 第一公民
- `revitcli check --phase tender` 只跑这个阶段的规则
- 看板加阶段轴 — 不只是"score over time",还有"per-phase score"
- 真正贴合 AEC 工作流(industry 里 ISO 19650 已经定义了 BIP / 等阶段,工具适配它)

### 范围(In)

- profile schema 加 `phases: [design, tender, construction, handover]` 顶级节点
- 每个 rule 可声明 `phase: <name>` 或 `phases: [a, b]`(默认 all)
- `revitcli check --phase X`,默认从环境(env / git tag)推断
- 当前阶段记入 `.revitcli/phase`,git-trackable
- dashboard 加 phase pill(不同阶段的 score 用不同颜色)
- 启用 lifecycle gate:`revitcli phase advance design tender` — 跑 tender 前置
  check;失败禁止推进

### 范围(Out)

- 自定义阶段名(只支持 ISO 19650 的标准 4 阶段)— 等用户要求
- 阶段间的工件继承 — 简单的"阶段拷贝模板"先放进 v3.2,完整工件继承推 v4.x

### 关键决策

**决策 1:阶段名硬编码还是可配置?**

候选 A:硬编码 4 个阶段(ISO 19650-aligned)
候选 B:profile.yml 自由定义

**结论:A 起步,B 在 v4.0 plugin pack 里**。先建立 industry 共识,再开放扩展。

### 实施分步

预计 3 周。

### 给 codex 的入口

```bash
"读 ISO 19650 part 2 的阶段定义.
用 superpowers:brainstorming 设计 phase-aware profile schema 扩展."
```

## 8. v4.0 — Plugin Ecosystem

### 价值主张

v1.5 spec 里写过:"自定义 fix strategy 插件机制 — 第一版只暴露内置 strategy,
不开放自定义脚本"。该决策 v1.5–v3.x 都有效;v4.0 反转。

理由:

- v3.0 federation 让 profile 共享变得 frictionless
- 但 profile 写不出来的就只能靠"加新内置规则" — 项目维护者瓶颈
- 社区想加 "Chinese national standards naming" / "Brazil's NBR 16280" 这种
  地区性规则 → 必须开放扩展点

### 创新度

**WASM 沙箱** — 用户写自己的 rule 用 Rust / AssemblyScript / TinyGo 编译成
WASM,RevitCli 用 [Wasmtime.NET](https://github.com/bytecodealliance/wasmtime-dotnet)
载入并安全执行。

技术上:

- 沙箱隔离 — 用户代码不能读写 fs / 网络
- 跨语言 — Rust / Go / TS 都能写
- 性能 — 接近 native

业界状态:

- TruffleHog / Semgrep / Datadog 用 WASM 做用户规则 → 已成熟模式
- AEC 行业**完全没人这么干** — 又一道护城河

### 范围(In)

- 插件包格式:`.revitcli/plugins/<name>.wasm` + `<name>.toml`(metadata)
- WASM ABI:`check_rule(snapshot_json) → issues_json`(简单 JSON 边界)
- `revitcli plugin install <git-url>` / `plugin list` / `plugin remove`
- 沙箱保护:无 fs 访问,无网络,执行时间上限
- 启动种子:5 个示例插件(Rust + TS 各一些),覆盖三类用例
  - Custom check rule
  - Custom fix strategy
  - Custom export post-processor

### 范围(Out)

- WASM debugger / profiler — 插件作者自己用 wasmtime 调
- 插件 marketplace — 走 federation registry(v3.0)就够了,不再独立做
- WASI preview2 高级特性 — 用稳定 preview1

### 关键决策

**决策 1:WASM 还是 .NET assembly?**

候选 A:.NET assembly + AssemblyLoadContext 隔离
候选 B:WASM via Wasmtime
候选 C:JS via Jint(嵌入 JS engine)

**结论:候选 B**。.NET assembly 隔离不严格(反射可逃);JS 性能 + 类型 弱;WASM
沙箱业界已成熟,跨语言。

### 风险

- **Wasmtime.NET binary size** — 增加 ~20MB CLI 安装。考虑独立 `revitcli-plugin`
  二进制(可选下载)
- **沙箱漏洞** — 任何 sandbox 都有逃逸风险。**强烈建议**插件签名 + 仅信任 verified
  registry 来源
- **ABI 演化** — JSON 边界稳定但内部 schema 变。坚持 schema versioning

### 实施分步

预计 8–12 周(包括 spec 1w,WASM runtime 集成 2w,ABI 设计 + 5 示例插件 4w,
沙箱测试 + 文档 2w)。

### 给 codex 的入口

```bash
"读 https://github.com/bytecodealliance/wasmtime-dotnet 的 README + examples.
用 superpowers:writing-plan 详细规划 v4.0 plugin runtime."
```

## 9. 跨版本约束(沿用 v1.5–v2.0 §9)

### 1. 兼容性

- `IRevitOperations` 接口变更必须**附加而非破坏**
- profile schema 改动必须保留 `version: 1` 解析路径,新字段必须有默认值
- snapshot `schemaVersion` 维持向前兼容
- journal.jsonl 字段只能附加

### 2. 跨平台

- CLI 端代码必须在 macOS / Linux 编译过
- Windows-only 路径用 `RuntimeInformation.IsOSPlatform(OSPlatform.Windows)` 守护
- 任何 `\\` 路径分隔符不进 main

### 3. 测试

- 每个新命令至少 5 个测试 fact(happy + 4 个 edge)
- WASM 插件运行需要至少 3 个沙箱逃逸测试用例
- 涉及 Revit API 的部分**禁止 mock 数据库**;走 addin 端真实集成 + smoke 脚本

### 4. 文档

- 每个 milestone 配 `docs/superpowers/specs/` + `docs/superpowers/plans/`
- README "Commands" 表必须更新
- CHANGELOG 必须列 Added / Changed / Backward compatibility / Known carry-forward
- 新版本必须配独立设计文档(类 v2.1 / v3.0 等),供 codex 接力

### 5. 性能基线

- 每个版本不能让 v1.5–v2.0 §9.5 已锁基线倒退
- 新引入路径(WASM 插件 / federation 网络调用)各自有独立性能预算

### 6. 安全

- 任何引入网络 / 外部代码执行的能力(v3.0 federation / v4.0 plugins)必须
  configure deny-by-default
- profile 安装前默认走 SHA / 签名校验
- WASM 插件运行前默认禁用网络 / fs
